# 分叉 0.11.3-4 发布记录：系统日历同步卡死与重复事件

日期：2026-10-25。基线：`main` / `3f184acd`（含 `5b3b822a` 的 NDK 覆盖输入）。本记录说明这一版修掉的两个现象、根因定位过程与验收边界。

## 1. 用户报告

HarmonyOS 6 安卓兼容层上，OneTHU-Fork 有两个独立表现：

1. 启动后约 8~25 秒内做滑动、打开左侧抽屉、点日程等操作会概率性黑屏闪退；后台挂起一小时回来会黑屏且不自愈。
2. 系统日历里积累出大量重复事件，同一日程最多重复二十余份。

## 2. 定位过程与结论

前两轮假设均被实验否定：NDK 版本（r28c 与 27.1 都崩）与分叉代码差异（上游代码走同一管线也具备同样条件）都不是决定因素。决定性证据来自用户按步骤复现：

- 点「开启并同步」后界面显示「开启中」约十秒，期间任意滑动即闪退；
- 每点一次就多出整整一整套事件；
- 彻底卸载重装后不再闪退，也不再重复写入。

第三条把范围收窄到「持久化配置里开着自动同步」。Tauri 的 Android 插件命令由 JNI 在 IPC 线程上同步执行（`PluginManager.runCommand`），执行期间上游持有 plugins 互斥量；日历同步一次要跑数千条 provider 操作，于是主线程取值受阻，界面卡死并最终闪退（与上游 tauri#14694 的死锁形态一致）。崩溃点落在「插入已提交、删除旧事件尚未执行」之间，因此每次尝试都留下一整份额外副本；启动 20 秒后的自动同步（`initSystemCalAutoSync`）同样触发，正是最初那个「8~25 秒窗口」。卸载重装清空了配置、`enabled=false`、自动同步不再运行，于是「好了」——不是数据脏，是功能被关掉。

## 3. 修复

`apps/desktop/src-tauri/plugins/onethu-calendar/` 原生侧三处：

| 改动 | 位置 | 作用 |
| --- | --- | --- |
| `sync` / `removeCalendar` 立即返回，provider 事务交给单线程执行器，结果回主线程 resolve | `OnethuCalendarPlugin.kt` | 不再长时间占用 IPC 线程，滑动不再撞死锁 |
| 镜像改为先按 `CALENDAR_ID` 清空整个专属日历、再写入 | `OnethuCalendarPlugin.kt`、`CalendarMirror.kt` | 中断后再同步是收敛，不是再叠加一份；历史重复副本一次清空 |
| 删除计数不符不再抛错 | `OnethuCalendarPlugin.kt` | 旧实现在鸿蒙上因 provider 返回值不可靠而报「旧事件清理未完成」，前端重试又整份重写，是放大器 |

语义变化记录在 `replaceCalendarMirror` 的注释里：专属日历归应用所有、每次全量重建，因此失败时留下空日历可自愈，而留下旧副本不可接受。对应单元测试同步改写为「先清空再写入」的六条断言。

## 4. 验收

- 用户真机（HarmonyOS 6）：`0.11.3-93` 上点「开启并同步」后，在「开启中」期间反复滑动、切 Tab、点日历按钮均不再闪退，写入完成且日历只剩一份。
- `node tools/system-calendar-state-test.mjs`：28 项通过（原生与网络均已打桩）。
- `node tools/fork-build-test.mjs`：分叉构建形状护栏通过，含版本 `0.11.3-4` 与正式版分离、Android 包名与签名缺省改名。
- APK 内容复核：`classes.dex` 含新字面量「同步参数无效」、旧字面量「专属日历尚未移除」已消失，确认打进去的是打过补丁的 Kotlin。

## 5. 已知边界

- 只验证了用户这一台鸿蒙设备；其它 ROM 上 provider 行为更规范，本改动不回退它们的行为（清空整份专属日历本就是原设计契约）。
- 上游正式版与本分叉共用系统日历本地账户名 `OneTHU`，两个包同时开启同步会互相认领同一个「OneTHU 日程」日历。本版未改账户名（改名会让现有日历变成孤儿），建议只保留一个包开启同步。
- 首次同步会清空并重建整份专属日历：若用户手动往「OneTHU 日程」里加过事件，那些事件会被移除。
