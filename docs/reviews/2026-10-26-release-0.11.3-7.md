# 分叉 0.11.3-7 发布记录：系统日历同步的进程级闪退

日期：2026-10-26。基线：`main` / `e26c7d7b`。本版修掉的是 0.11.3-4 引入、0.11.3-5 未能解决的一个新故障：**只要专属日历里已有事件，任何一次同步都会让进程直接消失**。

## 1. 用户报告

HarmonyOS 6 安卓兼容层，真机：

1. 进入一门课程、看过 50+ 文件的列表后突然闪退（无卡顿、无黑屏）。
2. 重启后崩溃点随机：点「发送测试通知」、切设置项、点日程页日历按钮，各崩一次。
3. 关掉「系统日历同步」后，以上路径全部正常；一开启就复发。

## 2. 定位过程

第 3 条是决定性对照：崩溃源在系统日历同步的原生链路，与用户当时在哪个界面无关（同步跑在后台线程，用户点什么都会“赶得上”）。

后续用三组真机实验排除假设：

| 实验 | 结果 | 排除 |
| --- | --- | --- |
| 「清空后开启」写入 226 条（空表） | 成功（两次） | 排除插入路径、`applyBatch`、提醒 back-reference |
| 「清除系统日历」（删日历行 + 级联删事件） | 成功 | 排除 provider 的级联删除能力 |
| 日历里已有 226 条时同步（新增一条日程触发） | 崩，且旧事件一条未删 | 锁定「查询 + 批量删除」这一段 |

崩溃发生在删除事务内部：进程被带走时事务未提交，所以旧事件完整保留——这解释了为什么“日历里还是原来那 226 条”。而 0.11.3-4 恰好把清空实现从“逐条 `_ID=?` 删”改成了“先查 226 个 id 再拼 `_ID IN (?,…×200)` 批删”，后者是唯一进入稳态路径的长参数列表语句。

## 3. 修复

`apps/desktop/src-tauri/plugins/onethu-calendar/`：

| 改动 | 位置 | 作用 |
| --- | --- | --- |
| 同步改为差异驱动（`planSync` 多重集差） | `CalendarMirror.kt`、`OnethuCalendarPlugin.kt` | 内容没变时 0 次 provider 写，删除原语彻底移出稳态 |
| 删除只按单条 `_id=?` | 同上 | 不再出现长 `IN` 参数列表 |
| 提醒分钟数用一次 `Reminders` 全表查询 + 内存关联 | `OnethuCalendarPlugin.kt` | 读提醒也避开长 `IN` 子句 |
| 全天事件先换算 UTC 零点再参与签名、文本两侧 `normText` | `CalendarMirror.kt` | 回读与写入逐字段可比，避免退化成“每次全删全插” |
| 桥接改 `run_mobile_plugin_async` | `src/commands.rs` | 不再把 tokio worker 挂死在阻塞等待上 |
| 后台执行器 `catch Throwable` | `OnethuCalendarPlugin.kt` | Error 级异常转可见错误，不再掀进程 |
| 连续失败 3 次熔断自动跟随 | `src/state/systemCal.ts` | 打断“崩 → 指纹未落盘 → 下次启动重试 → 再崩”的循环 |
| 面包屑落盘 + `sync_trace` 命令 | `OnethuCalendarPlugin.kt`、`src/commands.rs`、`src/lib/diagnostics.ts` | 兼容层上 adb 不可用，靠它把死亡边界带出来 |

语义变化：`replaceCalendarMirror`（清空 + 全量重写）被 `planSync`（按内容签名的多重集差）取代。幂等性不变——期望集合不变则结果不变；重复副本仍然自愈（期望 1 份、现有 3 份 → 删掉多的 2 行）。macOS 仍走 EventKit 的窗口内全量重写，本版未改动其行为，`SyncResult.unchanged` 恒为 0。

## 5. 已知边界

- 匹配键是内容签名，不是稳定 uid：Android 的 `Events` 表对非 sync-adapter 应用不开放可写 UID 列。因此**用户若在系统日历里手改了某条事件的时间或标题**，下次同步会把它视为“消失 + 新增”（删一插一），而不是原地更新。
- 提醒只比较“第一条提醒的分钟数”；同一事件存在多条提醒时以第一条为准。
- 只验证了用户这一台鸿蒙设备；其它 ROM 上差异同步同样成立（只是从“能用”变成“更省”）。
- 上游正式版与本分叉共用本地账户名 `OneTHU`，两个包同时开启同步会互相认领同一个「OneTHU 日程」；建议只保留一个包开启同步。
